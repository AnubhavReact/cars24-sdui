# AI Workflow Evidence

## Tool stack

- **Claude Code** (Sonnet 5), used agentically end-to-end: schema design,
  renderer/action code, editing `home.json` by hand and via script, running
  `adb`/`uiautomator`/`logcat` directly to drive and inspect the emulator,
  running Gradle release builds, and reading back screenshots to verify
  UI state visually rather than assuming from code.
- **Android Studio emulator** (Pixel_7 AVD, Android 16) as the only device
  used -- no physical device was available this session (see `PERF.md`'s
  methodology caveat).
- Working mode was mostly **high-level direction + autonomous execution**,
  not a rapid prompt-by-prompt chat loop: the user set the goal and
  approved checkpoints (schema design, then renderer, then perf, etc.);
  most implementation decisions, live-device verification, and bug-catching
  happened inside a single agentic turn rather than through many small
  back-and-forth prompts. That shapes the "prompt → outcome" stories below
  differently from a typical copy-paste-into-chat workflow: the interesting
  moments are less "I rejected what the AI typed" and more "the AI's first
  approach was wrong and live testing against the real emulator caught it
  before it shipped."

## Context / rules files

- `CLAUDE.md` / `AGENTS.md` (auto-generated by `create-expo-app`'s
  `blank-typescript` template, kept as-is): a one-line pointer to check the
  exact-versioned Expo docs (`docs.expo.dev/versions/v57.0.0/`) before
  writing code, because this Expo SDK is new enough that generic
  knowledge/training data can be stale about its APIs. Kept deliberately
  minimal rather than writing a large custom rules file -- the project is
  small enough (one schema, one renderer, two screens) that most "rules" a
  bigger project would need (test conventions, folder ownership, etc.)
  don't yet apply.

## Three prompt → outcome stories

### 1. Wrong first fix for the Metro/emulator bundle crash

**What happened:** Right after the first `expo run:android` build, the app
crashed with `TurboModuleRegistry.getEnforcing(...): 'PlatformConstants'
could not be found` -- a classic "JS bundle doesn't match native binary"
error. My first diagnosis was correct (a *different* project's Metro
server was already running on port 8081, so this app's build was fetching
someone else's JS bundle), but my **first fix was wrong**: I ran a second
Metro instance on port 8082 and set `adb reverse tcp:8081 tcp:8082`,
assuming the app would reach the dev server via `localhost:8081` on the
device, which `adb reverse` would correctly redirect.

**What was rejected and why:** That fix didn't work -- the crash persisted
identically after reload. Rather than guess again, I read
`PackagerConnectionSettings.kt` from the installed `react-native` package
in `node_modules` to check what host RN Android actually uses on an
emulator, which confirmed it defaults to `10.0.2.2:8081` (the emulator's
alias for the host's real loopback), not `localhost:8081` -- so `adb
reverse` was never in the request path at all, and the app kept hitting
the *other* project's Metro on the host's actual port 8081 the whole
time. The eventually-correct fix (chosen with the user, who preferred not
to disturb their other running project) was pushing a SharedPreferences
override (`debug_http_host`) into the app's own preferences file via `adb
shell run-as`, redirecting only this app to `10.0.2.2:8082`.

### 2. Perf methodology: the first cold-start sample was misleading

**What happened:** Prompted (by the task itself, not a literal user
message) to measure release-build cold-start time via `adb shell am start
-W`, the first number recorded was `TotalTime: 6326` -- nearly 6.3 seconds,
which would have made the write-up look alarming and, worse, non-comparable
between the Static and SDUI variants if used inconsistently.

**What was rejected and why:** Rather than report that number, I ran a
second cold start immediately after (same build, same device, just
force-stop + relaunch) and got `TotalTime: 322` -- roughly 20x faster. The
first number included one-time APK verification/ART compilation overhead
from right after `adb install`, not representative of a real repeated
cold-open. The methodology in `PERF.md` was rewritten to explicitly discard
the first post-install launch and average only repeat cold starts, with
this exact discrepancy called out in the write-up as the reason why, rather
than silently picking whichever number looked better.

### 3. Schema design: rejected the "one component per section" default

**What happened:** When designing the JSON schema against the 13-section
home-page inventory, the path of least resistance -- and the one most
SDUI-tutorial examples default to -- is one component type per visual
section: `carCard`, `loanRail`, `showroomCard`, etc. That would have been
faster to author for this one screen.

**What was rejected and why:** I explicitly reasoned through the brief's
round-1 test (a screen this system wasn't built for, judged on % rendered
with JSON-only changes) and concluded a per-section registry would score
near-zero on that test, since every new visual shape would need a new
component type. Rewrote the design around ~13 generic layout/content
primitives (`stack`/`row`/`carousel`/`grid`/`list` +
`text`/`image`/`icon`/`badge`/`button`/`divider`/`spacer` + `tappable`)
that compose to produce every section instead, accepting more verbose JSON
payloads as the trade-off. Full reasoning in `docs/SCHEMA.md`.

## One AI failure

**Incident:** When wiring the SDUI renderer's tap handling, I (Claude) wrote
`HomeScreen.tsx` with a `ScrollView` whose content started at `y: 0`, with no
top padding for the Android status bar -- I only applied the status-bar
inset (`Platform.OS === 'android' ? StatusBar.currentHeight : 44`) to the
*navigation-stack overlay*, and forgot to apply the same `topPad` to the
main scrollable content. Visually this looked fine on a screenshot (the
purple header just extended up under the translucent status bar), so it
read as correct.

**How it was caught:** Testing the `openSheet` action (tapping the location
picker) live on the emulator via adb -- the tap dispatch never fired, with
no error, no crash, nothing in the logs. Same for the profile-icon tap at a
similar height. Tapping a tab chip lower on the screen worked fine. That
pattern (works below a certain y, silently fails above it) pointed at a
touch-region conflict rather than a rendering bug -- the top ~130px of
content, though visually correct, was sitting under Android's status bar,
which was still intercepting touches there even though the app drew
(translucent) content underneath it.

**Fix:** added `contentContainerStyle={{ paddingTop: topPad }}` to the main
`ScrollView` so real content starts below the status bar inset, matching
what was already done for the overlay.

**Why this is a good example of a class of AI failure:** it's a bug a
screenshot alone won't catch -- the layout looked pixel-correct, and only
live touch-interaction testing on a real device/emulator surfaced it. It's
a reminder to verify interactive behavior, not just visual output, when
reviewing AI-written UI code.

## Verification strategy

- TypeScript compiled clean (`npx tsc --noEmit`) after every schema/renderer
  change before reloading on-device -- caught type errors (e.g. `Image`
  wanting `ImageStyle` not `ViewStyle`) before ever touching the emulator.
- Every renderer change was verified by actually reloading the app on the
  Pixel_7 emulator (via adb) and screenshotting the result -- not just
  trusting that the code "looked right."
- Action dispatch (`navigate`, `openSheet`) was verified by tapping the real
  emulator via `adb shell input tap` at coordinates pulled from
  `uiautomator dump`, and confirming the expected state change both via a
  temporary `console.log` in the dispatcher (checked against `adb logcat`)
  and a follow-up screenshot -- not assumed from reading the code. The
  temporary log was removed once confirmed working.
- Perf numbers were pulled from real `adb shell am start -W` output and
  `adb logcat`-read JS timestamps on an actual release build, not
  estimated or fabricated -- including reporting the awkward first-launch
  outlier (see story #2 above) instead of quietly discarding it without
  explanation.
- The unknown-component and versioning fallbacks were confirmed on-device
  in both directions: visible dev-mode placeholder in a debug build,
  confirmed silent (no crash, no visible artifact) in the actual release
  build used for perf measurement.
