# AI Workflow Evidence

## Tool stack

- **Claude Code** (Sonnet 5), used agentically end-to-end: schema design,
  renderer/action code, editing `home.json` by hand and via script, running
  `adb`/`uiautomator`/`logcat` directly to drive and inspect the emulator,
  running Gradle release builds, and reading back screenshots to verify
  UI state visually rather than assuming from code.
- **Android Studio emulator** (Pixel_7 AVD, Android 16) as the only device
  used -- no physical device was available this session (see `PERF.md`'s
  methodology caveat).
- Working mode was mostly **high-level direction + autonomous execution**
  for implementation (the user set the goal and approved checkpoints --
  schema design, then renderer, then perf, etc. -- while most
  moment-to-moment code and live-device verification happened inside
  agentic turns), **plus direct user QA against the real app**, which is
  where the sharpest correction in this build came from (see story #3
  below): the user installed and used the actual Cars24 app themselves,
  found a place where this build's behavior didn't match it, and rejected
  a shipped design decision directly. That combination -- AI executing
  fast, human verifying against ground truth the AI didn't check carefully
  enough -- is the pattern this whole workflow leaned on.

## Context / rules files

- `CLAUDE.md` / `AGENTS.md` (auto-generated by `create-expo-app`'s
  `blank-typescript` template, kept as-is): a one-line pointer to check the
  exact-versioned Expo docs (`docs.expo.dev/versions/v57.0.0/`) before
  writing code, because this Expo SDK is new enough that generic
  knowledge/training data can be stale about its APIs. Kept deliberately
  minimal rather than writing a large custom rules file -- the project is
  small enough (one schema, one renderer, two screens) that most "rules" a
  bigger project would need (test conventions, folder ownership, etc.)
  don't yet apply.

## Three prompt → outcome stories

### 1. Stale-data caching bug, caught by comparing against the real app

**What happened:** Every navigate destination (`listing`, `car_detail`)
went through a mock server with a simulated 450ms network delay. I wrote
the destination screen to reset to a loading spinner on *every*
navigation, including a repeat visit to a screen+params combination
already fetched earlier in the same session -- so reopening the exact
same car detail page a second time replayed the full 450ms wait and
spinner again, every single time.

**What the user rejected and why (verbatim):** *"every time i navigate
every time loader ? why if one time data is loaded then next time come
then again loader , actual cars24 dont do this it showing stale data
check cars24 also"* -- a direct instruction to go verify against the real
app rather than take my behavior as correct by default.

**What I did:** opened the real Cars24 app fresh, tapped into a car's
detail page (skeleton loader, as expected on a first visit), went back,
tapped in again -- content appeared *instantly*, no loader at all,
confirmed by screenshot. Built an in-memory stale-while-revalidate cache
(`src/server/screenCache.ts`) keyed by `screenId + params`: first visit
shows the loading state and caches the result; every later visit to the
same key renders the cached `Screen` immediately with zero loading state,
while a fresh fetch still happens invisibly behind it. Verified live by
screenshotting a revisit at a 150ms delay after the tap -- well under the
450ms fetch time -- confirming the fast path was a genuine cache hit, not
luck.

### 2. A systemic styling bug, caught by comparing SDUI vs. Static screenshots side by side

**What happened:** The schema's `text` node has a `variant` prop
(`title`/`subtitle`/`body`/`caption`/`label`), clearly intended to carry a
typography preset. I never actually implemented it -- `Renderer.tsx`'s
`text` case only ever applied a node's explicit `style`, and completely
ignored `props.variant`. Any text node relying on `variant: "title"` alone,
with no explicit `fontSize`/`fontWeight`, silently rendered as plain
unstyled text. This shipped invisibly for most of the session because it
doesn't look "broken" in isolation, just slightly thin -- it only became
obvious in direct comparison.

**What the user rejected and why:** the user placed SDUI and Static
screenshots of the same section side by side and pointed at the exact
mismatch: *"see you dont update the styling issue... see buy car, best
deals for you text in sdui, compare to static ui"* -- Static's headings
were correctly bold (hardcoded `fontSize: 18, fontWeight: '700'`), SDUI's
were not.

**What I did:** grepped `home.json` programmatically for every text node
using `variant` without an explicit font override -- **19 nodes**, mostly
section titles across the whole page. Root-caused it to the renderer
never reading `props.variant` at all, and fixed it by adding a
`TEXT_VARIANT_STYLES` preset map applied as the base style, with the
node's explicit `style` still overriding on top (same precedence already
used for button/badge variants). The same investigation also surfaced two
related Static/SDUI parity gaps the user had separately flagged (a
missing favorite-heart toggle, and the "Buy used car" tab still
navigating in Static instead of swapping content in place, unlike the
already-corrected SDUI version) -- fixed in the same pass, since a fair
Static-vs-SDUI perf comparison requires matched content, not just matched
architecture.

### 3. Tab-navigation design, corrected by direct comparison against the real app

**What happened:** Early in the build, I (Claude) explored the real Cars24
app to decide how the category tabs should behave, and tapped "Buy used
car" using a raw eyeballed screenshot coordinate (before this session
adopted the discipline of reading exact bounds via `adb shell uiautomator
dump` for every tap). That tap landed on a full listing/search screen, so I
concluded the tabs `navigate` to a new screen, and built the whole action
around that: `navigate` carrying a `category` param, later extended into
the param-driven "listing" destination screen.

**What the user rejected and why:** After the app was working end-to-end,
the user reviewed the running app against the real Cars24 app themselves
and flagged it directly: *"buy used car me navigation nhi hai sirf tab
switch hai actual cars24 me"* -- there's no navigation for "Buy used car,"
it's just a tab switch in the actual app. This was a real prompt catching a
real, shipped, wrong design decision -- not something I caught myself. I
re-verified by relaunching the real app fresh and tapping the tab using
exact bounds from `uiautomator dump` (`clickable area [226,424][528,614]`,
center far from my original guess), and the user was right: header, tab
bar, and bottom nav all stay identical, only the body content swaps.
Reworked `category_tabs` from `navigate` to `setState` + `visibleIf`
(reusing the same selected/unselected pattern already proven by the
favorite-heart toggle), gated every "All tab" section behind
`visibleIf: activeTab == 'all'`, and built a real "Buy used car" tab body
matching the verified real layout (2x2 category grid + a car rail).
Full trail in `docs/screen-inventory.md`.

## Bonus: a full live planning cycle (task → read → explore → questions → answers → review)

Everything above happened inside normal build turns. This one is different
on purpose: run as a standalone exercise, close to what round-1's "screen
you didn't build, plan it live" test will actually look like -- a task
handed over, clarifying questions asked and answered in real time, a
design converged on, **with implementation explicitly out of scope for
this exercise** (per direct instruction, see below) so the artifact here
is the planning conversation itself, not new code.

**1. Task given (verbatim):** *"okay so i have picked explore page in
cars24 ui so basically we have to deisgn it sdui , so currently we have a
child depend upon the figma now we need to update this page to we need to
change child code everytime so to reudce this we will create components
like this api payload send json and our child will render acc to that ?"*

**2. Read back to confirm understanding, before doing anything else:** I
restated the motivation in my own words (child code coupled to
Figma/design changes today; JSON payload + generic renderer decouples
that) and confirmed it matched, rather than assuming and moving straight
to implementation.

**3. Explored the real screen first** rather than guessing its content:
launched the real Cars24 app, navigated to the actual "Explore" tab,
screenshotted and scrolled through all 11 sections of its "Buy used car"
sub-tab, and live-tested tab-switch behavior by tapping between the four
top tabs.

**4. Two real questions surfaced while drafting JSON from scratch** for
this screen (not reusing `home.json` -- an explicit instruction: *"so dont
relate it to our existed home.json it fresh think you need to create a
json from scratch then ask me question based on this"*):
   - **Q1:** the ranked trending-car cards ("Verna ₹2L-11L") are a price
     range across a model's variants, not one specific listing -- what
     should tapping one navigate to?
   - **Q2:** the "01"/"02" rank number rendered behind/overlapping the car
     image has no equivalent in the current schema (no z-index/layering
     concept exists) -- extend the schema for real layering, fake the
     visual, or drop the effect entirely?

**5. Answers (verbatim):** *"so for question 1 basically it go to call
listing api , we will pass data through params and based on this get api
will call for listing and now for que2 the image and its list will come
from api we need to just render that list also if we need to show no we
willl add a layering and based on index we will show it"* -- resolved Q1
to `navigate` → `listing` with a new `model` param (reusing the existing
screen); resolved Q2 to adding real layering rather than faking it.

**6. A follow-up clarifying question, because the answer to Q2 was still
ambiguous** in one respect: does the server explicitly send each card's
rank value, or does the client compute it from the card's position in the
array? These have very different architectural implications (pure
declarative data vs. new renderer logic), so I asked rather than picking
one silently. **Answer:** *"yes most probably distinct and if not we will
pick the index"* -- server-sent by default, with an index-based client
fallback for resilience.

**7. Verification, not just conversation:** live-tested the two tabs I
hadn't checked yet ("Get loans", "Car check") on the real app rather than
assuming they matched the pattern already confirmed for the other two --
and found a real inconsistency: "Get loans" actually navigates to the
listing screen with an extra promotional banner prepended, while "Buy
used car"/"Sell car"/"Car check" all do the in-place `setState` swap.
This directly informed the tab-bar design below.

**8. Design review and convergence:** proposed making the tab bar itself
fully data-driven -- an array of tab definitions in JSON, each with its
own independent `onTap` (already a property of the existing schema, not a
new capability) -- so the real "3 tabs swap in place, 1 navigates"
inconsistency needs zero special-case client code, it falls out of the
existing per-node action design. Combined with one new primitive
(`layered`, for the rank-overlay effect) this produced a complete,
implementation-ready plan covering all 11 sections, with only one small,
well-justified schema addition. **Implementation was deliberately not
done** -- explicit instruction: *"so we need to make our tab component
based on the listing comes in json"* was a design direction to fold into
the plan, not a build instruction, and this whole exercise was framed
up front as *"just doing a agent and developer communication for
ai_workflow how i give you task and answers you questions."*

## One AI failure

**Incident:** When wiring the SDUI renderer's tap handling, I (Claude) wrote
`HomeScreen.tsx` with a `ScrollView` whose content started at `y: 0`, with no
top padding for the Android status bar -- I only applied the status-bar
inset (`Platform.OS === 'android' ? StatusBar.currentHeight : 44`) to the
*navigation-stack overlay*, and forgot to apply the same `topPad` to the
main scrollable content. Visually this looked fine on a screenshot (the
purple header just extended up under the translucent status bar), so it
read as correct.

**How it was caught:** Testing the `openSheet` action (tapping the location
picker) live on the emulator via adb -- the tap dispatch never fired, with
no error, no crash, nothing in the logs. Same for the profile-icon tap at a
similar height. Tapping a tab chip lower on the screen worked fine. That
pattern (works below a certain y, silently fails above it) pointed at a
touch-region conflict rather than a rendering bug -- the top ~130px of
content, though visually correct, was sitting under Android's status bar,
which was still intercepting touches there even though the app drew
(translucent) content underneath it.

**Fix:** added `contentContainerStyle={{ paddingTop: topPad }}` to the main
`ScrollView` so real content starts below the status bar inset, matching
what was already done for the overlay.

**Why this is a good example of a class of AI failure:** it's a bug a
screenshot alone won't catch -- the layout looked pixel-correct, and only
live touch-interaction testing on a real device/emulator surfaced it. It's
a reminder to verify interactive behavior, not just visual output, when
reviewing AI-written UI code.

## Verification strategy

- TypeScript compiled clean (`npx tsc --noEmit`) after every schema/renderer
  change before reloading on-device -- caught type errors (e.g. `Image`
  wanting `ImageStyle` not `ViewStyle`) before ever touching the emulator.
- Every renderer change was verified by actually reloading the app on the
  Pixel_7 emulator (via adb) and screenshotting the result -- not just
  trusting that the code "looked right."
- Action dispatch (`navigate`, `openSheet`) was verified by tapping the real
  emulator via `adb shell input tap` at coordinates pulled from
  `uiautomator dump`, and confirming the expected state change both via a
  temporary `console.log` in the dispatcher (checked against `adb logcat`)
  and a follow-up screenshot -- not assumed from reading the code. The
  temporary log was removed once confirmed working.
- Perf numbers were pulled from real `adb shell am start -W` output and
  `adb logcat`-read JS timestamps on an actual release build, not
  estimated or fabricated -- including reporting an awkward first-launch
  outlier (`TotalTime: 6326` right after `adb install`, vs. 98-322ms on
  repeat launches of the identical build -- APK verification/ART
  compilation overhead, not representative) in `PERF.md`'s methodology
  section instead of quietly discarding it without explanation.
- **Side-by-side screenshot comparison caught two real bugs this
  session** that neither automated testing nor a single-screen eyeball
  check would have: the missing text-variant typography (story #2 above)
  and the Static/SDUI content-parity gaps (favorite heart, tab content) --
  both only became obvious once the same content was placed next to its
  supposedly-identical counterpart.
- The unknown-component and versioning fallbacks were confirmed on-device
  in both directions: visible dev-mode placeholder in a debug build,
  confirmed silent (no crash, no visible artifact) in the actual release
  build used for perf measurement.
- **A visual assumption was proven wrong with pixel data, not eyeballing.**
  Building the `car_detail` screen, the CTA buttons and a badge looked
  visually like plain unstyled text instead of colored pills -- easy to
  second-guess as "maybe that's just how the screenshot compressed." Instead
  of trusting the eyeball read, I sampled actual pixel RGB values at the
  button's exact `uiautomator`-reported bounds with Pillow: pure white/light
  gray, no blue anywhere the variant's `#4B3AF0` background should have
  been. That confirmed a real bug rather than a rendering-quality artifact,
  and pointed straight at `styleUtils.ts`: `toViewStyle`/`toTextStyle`
  always returned every style key, including explicit `undefined` for
  anything unset -- which, merged into a style array like
  `[base, variantStyle, style]`, overwrites the variant's default styling
  the moment a node sets any unrelated custom style property (this
  specific case: a button given `width: 160`, or a badge given
  `marginTop: 8`). Fixed at the root by stripping undefined keys before
  returning, and then grepped the rest of `home.json` to confirm no
  already-shipped node had silently hit the same bug.
